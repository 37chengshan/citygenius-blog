<b>一句话总结</b>
今日小票是我做的 Android 记账 App：读支付宝、微信的支付通知自动记一笔，晚上把这一天打印成一张小票。这篇主要讲它是怎么做出来的。我给每个模型分好了活：Opus 5.5 规划和写前端，拿不准的问题问 Fable 5.2，omp 里的 DeepSeek 写后端和杂活，Haiku 搜索调研，Codex 交叉审查和生图。界面靠一个专门打磨的 UI skill，需求靠一份逐字的原话记录。三周下来开发仓库 497 个提交、911 处单元测试，v0.5.0 已经能装到手机上用。
</div>

做这个 App 的契机是支付宝的一个智能体比赛。比赛有个许愿池，去重以后有 812 条需求，最大的一类是消费记账和财务，149 条。支持数最高的一条是「帮我揪出悄悄扣钱的自动续费」，298 个人点了支持。看到这些数字，我确定这是很多人真想要的东西。

我的想法很简单：钱花出去的时候自动记一笔，晚上把这一天打印成一张小票，有明细、有合计，再配一句不说教的点评。它叫「今日小票」，一个 Android 原生 App，加一个 Web 版和一个自己搭的 Node 服务。

我一个人，要做三端。这篇会介绍产品，但主要讲一个想法是怎么一步步变成能装在手机上用的 App 的：怎么把想法拷问清楚，怎么给几个模型分活，用了哪些 skill，又踩了哪些坑。这些做法换个项目也能用。

## 问题

产品上的问题很清楚。记账 App 已经很多了，难的是坚持记，每花一笔都要打开 App、选分类、输金额，几天以后大部分人就不记了。另外，AI 和钱放在一起，最怕它顺手编一个数字。

开发上的问题更多。一个人做三端，只能靠 AI，但用了两天我就碰到三件事。第一，AI 写的功能是对的，界面却很丑，我在真机上看了直接吐槽「按钮什么的做的好难看」。第二，换一个会话，之前定好的东西又被改回去，已经删掉的示例小票又冒了出来。第三，同时开太多 agent，它们改来改去，反而什么都做不完。

后面的做法，基本都是在解决这三件事。

## 做法

### 先把想法拷问清楚

动手写代码之前，我先用 grilling 这个 skill 让 AI 反过来追问我：主角是谁，做 App 还是 Web，怎么入账，数据能不能出手机。两轮问下来，定了 11 条决策（D1 到 D11），写进 `docs/SPEC.md`。我没明确回答、按推荐默认的，标上「假设」，随时可以推翻。

定稿当天我就推翻了一条大的。最早的方案是 iOS 上截图识别，后来发现 Android 授权后能读到支付宝和微信支付的通知，可以真正做到不用动手记账，就改成了只做 Android。之后每次改需求，都要在 SPEC 里写明日期和原因。这样任何一个新开的会话读完 SPEC，就知道现在要做什么、为什么。

### 给每个模型分好活

<figure class="illu method">
  <img src="/citygenius-blog/assets/project-xiaopiao-team-zh.webp" alt="今日小票开发中的模型分工图" width="1600" height="740" loading="lazy" />
  <figcaption>今日小票开发时的分工。我负责定方向、真机验收和拍板；下面五个模型各管一摊，彼此通过同一个仓库、SPEC、原话记录和 skill 共享上下文。</figcaption>
</figure>

现在的分工里，五个模型各管一摊。

- **Opus 5.5** 负责规划和写前端。它拆任务、写规格，App 的主线和界面它自己写。开发仓库的提交署名里它出现了 180 次，从第一天到最后一天都有。
- **Fable 5.2** 是我拿不准时去问的。方案定下来之前，或者同一个错第二次出现、正常调试卡住的时候，就请它看一眼。
- **omp 里的 DeepSeek**（deepseek-v4.1-flash）写后端和杂活。Opus 先把 Web 和服务端的规格写细，交给它实现，再由 Opus 最后打磨；真机测试也常交给它跑。提交署名 70 多次。
- **Haiku** 负责搜索和调研：翻仓库、查文档、去 GitHub 找开源实现。它只返回结论和文件位置，主会话不用自己读一大堆文件。
- **Codex** 负责交叉审查和生图。换一个模型来挑错，能发现同一个模型自己看不出的问题；落地页用的照片也是它生成的。

这套分工不是一开始就想好的。第一天我用「分道」的办法，让几个 Sonnet agent 并行搭出了第一版：capture 管数据和通知识别，receipt 管主题和小票页，insights 管统计和徽章，merchant 管小店版和小游戏，每个 agent 只能改自己道里的文件，在自己的 worktree 分支上提交，不 push、不 merge。机器只有 16 GB 内存，四个 agent 共用，规则里写死了只跑快速编译、不许开模拟器。

第二天我让主会话只统筹、不亲自写代码，实现全派给 worker。当晚就出了问题，我的原话是「代理直接改来改去根本完成不了任务」。于是全部叫停：App 主线改回 Opus 自己写，只留一个 omp 做 Web 和真机测试，一个 Codex 干杂活，并行 worker 以后最多 5 个。

我的体会是，并行适合边界清楚的活，比如按规格实现后端、分道搭骨架。App 主线这种牵一发动全身的部分，交给一个模型从头写到尾更稳。

### 把原话记下来

分工解决了「互相改坏」，但没解决「忘了我要什么」。开工第二天真机验收，我发现自己在反复说同样的话，比如「为什么又有示例小票了，你现在就是 mock 数据啊」「不是我说的很清楚了啊」。

后来我在开发仓库里加了一份「原话记录」，把我说过的产品和设计要求按时间逐字记下来，错别字和口语都不改，每条编号，再写清「落到了哪」。规则只有一条，有冲突时以时间更晚的原话为准。设计文档引用时只写编号，不转述，避免一层层传话传歪。上面那段分工的变化，也全都记在这份文件里。

让 AI 写代码不难，难的是让它记住我说过的话。

### 专门做一个 UI skill

「界面丑」这个问题，我让 AI 去拆别人的 App，再把学到的东西写进我们自己的 UI skill，叫 `app-ui-design`，省得每次都靠吐槽。以后不管哪个模型写界面，都先读它。

它的核心是一个固定顺序：结构 → 层级 → 间距 → 字 → 色 → 细节 → 动效，后面的步骤救不了前面的错。AI 做的界面丑，几乎都是跳过了前面的步骤，直接上色、全靠字号拉层级、所有按钮都实心。所以 skill 里有一条很具体的规则：一屏最多一个实心主按钮，次要操作用线框或浅底，辅助操作用纯文字。

素材来自 Refactoring UI 的 20 条原则、Emil Kowalski 的设计工程 skills（MIT 许可）、Apple 的流体界面分享和 Material 3、iOS 的设计规范，都用自己的话重写过。还有一份竞品拆解笔记：比如另一个 App 的「用量小票」，我们把 25 秒的录屏按每秒 2 帧抽了 50 帧，一帧帧量出它的字号只有 4 档，纸从屏幕顶部往下「吐」，打印声是 7 段棘轮声。今日小票的打印动画就是照这个思路做的。

这个 skill 还要求用最坏情况的数据压测界面（超长的名字、空列表、很多条记录、加载失败），重要的部件先出几个方案并排比。我在真机上吐槽一次，就写进 skill 一次，下次所有模型都照着来。

### 其他用到的 skill 和工具

- **ego-browser**：所有网页任务都用它，打开 Web 版、截图、测交互。
- **android-remote-control**：一个 MCP，让 agent 直接操作我的真机。
- **animate**：做动效时按它的顺序决定要不要动、用什么曲线、怎么打断。
- **archify**：画架构图，下面那张就是用它生成的。
- **Orca**：派 omp worker、监督并行任务、收结果。
- **Figma**：设计系统的变量和组件，和代码里的 `Tokens.kt` 一一对应。

### 产品里的几个关键决定

  <img src="/citygenius-blog/assets/project-xiaopiao-arch-zh.webp" alt="今日小票系统架构图" width="1600" height="847" loading="lazy" />
  <figcaption>今日小票的系统架构。左边是两个入口：Android App 在手机上解析支付通知，红色虚线框里的原始数据不出手机，只有结构化字段发到云端；Web 版走同一套 API。右边的云端里，Agent 编排先查结构化账本和知识书，再调大模型生成回答，回答里的数字要过一道「必须有出处」的校验。</figcaption>
</figure>

记账靠 Android 的 `NotificationListenerService` 读支付通知，付款、免密扣费、先享后付、自动续费、收款、退款都能识别。看不到金额的红包和转账先记一笔「待填金额」。金额一律按整数「分」存，避免小数误差。

语音踩过一个坑。系统自带的 `SpeechRecognizer` 在我的 vivo 手机上从来不回调，界面一直显示「在听」。后来换成端侧的 sherpa-onnx，中文小模型 25 MB，边说边出字，再加一份记账热词表；「三十五块五」会先换成 35.5 再进账本，录音和模型都留在手机上。

问账本的时候，AI 不能自己算。服务端的 Agent 通过只读工具取数，比如查账、按分类筛选、和上周同期对比，再用结果组织语言，过程用 SSE 流式推到界面上。回答发出去之前还有一道校验，没有出处的数字不能出现。模型一开始只用 commandcode 的免费模型，现在线上主力换成了 DeepSeek v4.1 Flash，免费模型做后备，密钥只放在服务端。

从 10 月 27 日到 11 月 14 日，开发仓库的 main 分支上有 497 个提交。Android 端有 381 个 Kotlin 源文件，单元测试 103 个文件、911 处 `@Test`。提交署名里，Opus 5.5 有 180 次，Sonnet 有 84 次（集中在前两天分道的时候），omp 里的 DeepSeek 有 70 多次。

11 月 13 日在 GitHub 上发了 v0.5.0 的 APK，Android 8.0 以上能装。现在能用的有每日小票（打印、盖章、撕纸动效）、订阅侦探、用自然语言问账本、后悔模拟器，还有和家人朋友的小圈子，以及人格测试、决策转盘这类小游戏。

## 现状

现在是 0.5.1 体验版，还在每天迭代，比赛那边 12 月 5 日提交。小票上的点评还是模板生成的，接大模型的接口已经留好。「小店版」还只是探索方向。AI 的边界也在调，11 月 14 日我删掉了一条「所有选择都由人来做」的旧原则，它其实不是我定的，还把饮食搭配、健身计划这类建议都拦掉了；投资结论和医疗判断仍然不碰，也不会替你下单。

如果只从这篇带走三件事，我会选这三件。动手前先让 AI 把想法拷问清楚；给模型分好活，并行要设上限；吐槽一次，就写进 skill 或原话记录一次。

APK 和说明在 [GitHub](https://github.com/37chengshan/xiaopiao)，欢迎试用，也欢迎在 Issues 里提意见。

## 常见问题
### 为什么不让一个最强的模型全包？
不同的活需要的能力不一样。规划和写界面需要强模型盯全局；按规格写后端、跑测试这类边界清楚的活，交给更便宜的模型并行做更划算；搜索调研用小模型就够了。换一个模型做交叉审查，也更容易发现同一个模型自己的盲区。
### 几个 agent 同时写代码，不会互相改坏吗？
关键是先分道：每个 agent 只改自己那条道里的文件，共享文件谁都不碰，各自在 worktree 分支上提交，最后统一合并。并行的数量也要设上限，我现在最多开 5 个。
### 今日小票会把我的支付记录传到云端吗？
支付通知原文、账单原文和图片都在手机上解析，云端同步只用结构化字段。分享到圈子的小票只带分类合计，不带商户名和逐笔原文。不登录也能记账。
### 要买一台小票打印机吗？
不用。小票是屏幕上的动画，打印、盖章、撕纸都在 App 里完成。
