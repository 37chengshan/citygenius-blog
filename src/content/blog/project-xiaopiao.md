<b>一句话总结</b>
今日小票是我做的 Android 记账 App：读支付宝、微信的支付通知自动记账，晚上把一天的花销打印成一张小票。这篇主要讲它是怎么做出来的。我按各自的长处给模型分工：Opus 5.5 规划、写前端、派活，DeepSeek v4.1 Flash 写后端、干杂活、建知识库，Haiku 负责搜索、守住上下文，Codex 里的 GPT-6.1-sol 做交叉审查和生图，卡住时再问 Fable 5.2。手里只有 Claude 和 GPT 各一份最低档订阅，额度是整套系统要权衡的约束，不是分工的出发点。三周下来，开发仓库有 497 个提交、911 处单元测试，整套配置已经开源。
</div>

做这个 App 的契机是支付宝的一个智能体比赛。比赛有个许愿池，去重以后有 812 条需求，最大的一类是消费记账和财务，有 149 条；支持数最高的一条是「帮我揪出悄悄扣钱的自动续费」，298 个人点了支持。看到这些数字，我确定这是很多人真想要的东西。

想法很简单。钱花出去的时候自动记一笔，晚上把这一天打印成一张小票，有明细、有合计，再配一句不说教的点评。它叫「今日小票」，一个 Android 原生 App，加一个 Web 版和一个自己搭的 Node 服务。

我一个人做三端，手里只有 Claude 和 GPT 各一份最低档订阅。这篇会介绍产品，但更多篇幅留给开发：想法怎么被拷问成 SPEC，五个模型怎么分工，有限的额度怎么权衡，上下文怎么守住，吐槽怎么变成规则。我把这一整套叫作 harness，也就是套在模型外面的那层工程，包括分工、上下文、工具和检查。配置我整理成了一个开源仓库，文末有地址。

## 问题

产品上的问题很清楚。记账 App 已经很多了，难的是坚持。每花一笔都要打开 App、选分类、输金额，几天以后大部分人就放弃了。另外，AI 和钱放在一起，最怕它顺手编一个数字。

开发上的问题有三个，开工两天就全碰上了。一是 AI 写的功能对，界面却丑，我在真机上看完直接吐槽「按钮什么的做的好难看」。二是换一个会话，定好的东西又被改回去，删掉的示例小票又冒了出来。三是同时开太多 agent，它们互相改来改去，什么都做不完。

另外还有一个约束从一开始就在，那就是额度。最低档订阅按时间窗口计额度，Opus 这样的强模型很快就能把一个窗口用完，用完只能等。一个人做三端，代码量摆在那里，强模型的每个 token 都得花在刀刃上。

后面的做法，基本都在解决这三件事，同时在额度里做取舍。

## 做法

### 先把想法拷问清楚

写代码之前，我先用 grilling 这个 skill 让 AI 反过来追问我：主角是谁，做 App 还是 Web，怎么入账，数据能不能出手机。两轮问下来定了 11 条决策（D1 到 D11），写进 `docs/SPEC.md`。我没明确回答、按推荐默认的项标成「假设」，随时可以推翻。

定稿当天我就推翻了一条大的。最早的方案是在 iOS 上截图识别，后来发现 Android 授权后能读到支付宝和微信支付的通知，可以真正做到不用动手记账，于是改成只做 Android。之后每次改需求，都要在 SPEC 里写明原因。SPEC 是整个项目的 single source of truth（唯一可信来源），新开的会话读完它，就知道现在要做什么、为什么。

这一步也最省额度。需求在对话里定清楚，花的是几轮问答；没定清楚就开工，返工花掉的是成段的代码。

### 给每个模型分好活

<figure class="illu method">
  <img src="/citygenius-blog/assets/project-xiaopiao-harness.webp" alt="今日小票的 agent harness 架构图" width="1800" height="1439" loading="lazy" />
  <figcaption>今日小票的 agent harness。左边是我和 Opus 5.5 主会话；主会话只做规划、前端和派发：搜索交给 Haiku 子代理，后端和杂活经 Orca 派给 omp 里的 DeepSeek，omp 的活提交在单独的分支上，审查后才合进 main。Codex 做第二意见和生图，Fable 5.2 只在卡住时出场。左下是所有模型共用的上下文：AGENTS.md、SPEC、skills，以及和 Tokens.kt 同名的 Figma 变量。</figcaption>
</figure>

分工看两件事：这个模型最擅长什么，这件活要不要和别的活分开。规划和写界面要有人盯全局，写代码的和审代码的要分开，读得多、结论少的搜索不能挤进主会话。

- **Opus 5.5** 负责规划、写前端和派活。它拆任务、写规格、写 App 的界面主线，能拆出去的活全部派出去。开发仓库的提交署名里它出现了 180 次，从头到尾都在。
- **DeepSeek v4.1 Flash**（在 omp 里跑）写后端、干杂活、建知识库。这类活边界清楚、量大，按写好的规格就能做好，后端接口、成批的代码、知识库的资料收集和整理都归它。Opus 先把规格写细，它照着实现，最后再由 Opus 打磨。提交署名 70 多次。
- **Haiku** 负责搜索和调研，真正的作用是守住主会话的 context window（上下文窗口）。翻仓库、查调用链、找开源实现，这类活读的文件多、留下的结论少，让 Opus 自己读，等于用最贵的 token 读日志。Haiku 读完只交回一段 JSON：结论、文件位置、还缺什么。
- **Codex 里的 GPT-6.1-sol** 负责交叉审查和生图。换一家的模型来挑错，更容易看出 Claude 自己的盲区；落地页的照片也是它生成的。
- **Fable 5.2** 是顾问，只在三个时刻出场：定架构之前，同一个错第二次出现时，宣布高风险任务完成之前。

额度是在这套分工之上做的权衡。最低档订阅的窗口很紧，所以有几条取舍：Opus 的额度只花在规划、前端和合并上；量大的活优先给 DeepSeek，它不限量，可以放开用；读文件的活交给 Haiku，主会话不碰。

子代理的边界写死在配置的 frontmatter 里，比口头约定可靠。`search` 和 `grep` 只有只读工具；`audit` 多一个 Bash，但跑在 plan 模式下，只在隔离的 worktree 里审已经提交的代码。它们都声明了 `disallowedTools: advisor`，免得便宜的模型在后台偷偷调用贵的顾问；`omitClaudeMd: true` 让它们不加载主会话那份长长的规则，每次调用又省下一截。

DeepSeek 的活通过 Orca 派发。Orca 是一个多 agent 的 orchestration（编排）工具：主会话用 `run-create` 开一轮任务，用 `worker-start` 给每个 worker 一份自带上下文的说明，再用 `check --wait` 等结果回来，中间不用盯着。有一轮我并行派了三个 omp worker：两个做设置页和统计页的英文本地化，分别改了 2 个和 4 个文件，审完都合了进去；第三个做设置根页的转场，卡了 21 分钟，我叫停了，只留下 1 个有用的文件。worker 交付后先保留会话，下一个任务接着用，省掉重新读一遍仓库的 token。

这套分工也是一步步改出来的。第一天我用「分道」的办法，让几个 Sonnet agent 并行搭出了第一版：capture 管数据和通知识别，receipt 管主题和小票页，insights 管统计和徽章，merchant 管小店版和小游戏。每个 agent 只能改自己道里的文件，在自己的 worktree 分支上提交，不 push、不 merge。机器只有 16 GB 内存，四个 agent 共用，Gradle 构建要排队拿锁，规则里写死不许开模拟器。

第二天我让主会话只统筹、不写代码，实现全部派给 worker。当晚就出了问题，我的原话是「代理直接改来改去根本完成不了任务」。于是全部叫停：App 主线改回 Opus 自己写，并行的 worker 以后最多 5 个。

我的体会是，并行适合边界清楚的活，比如按规格实现后端、分道搭骨架、跑测试。App 主线牵一发而动全身，交给一个模型从头写到尾更稳，也更省额度，因为最烧额度的就是来回返工。

### 把原话记下来

分工解决了「互相改坏」，没解决「忘了我要什么」。开工第二天做真机验收，我发现自己一直在重复同样的话，比如「为什么又有示例小票了，你现在就是 mock 数据啊」「不是我说的很清楚了啊」。

后来我在开发仓库里加了一份「原话记录」，把我提的产品和设计要求按时间逐字记下来，错别字和口语都不改，每条编号，再写清「落到了哪」。规则只有一条，有冲突时以时间更晚的原话为准。设计文档引用时只写编号，不转述，免得一层层传话传歪。上面分工的每一次调整，也都记在这份文件里。

Anthropic 把这类事叫作 context engineering（上下文工程）。模型的注意力有限，放进上下文的每一行都应该有用。我的办法是把要记住的东西都写进文件，用到时再读。三家工具共用同一份 `AGENTS.md`，Claude、Codex、omp 读到的规则一字不差；skill 只放在一个目录里，用软链接挂到每个工具下面。会话太长时，有一个 hook 会在自动压缩过一次、上下文又涨到 38 万 token 左右时拦下来，让当前会话写一份交接文档，新会话读完接着干，不靠模型硬记。

让 AI 写代码不难，难的是让它记住我说过的话。

### 专门做一个 UI skill

针对「界面丑」，我让 AI 去拆解别人的 App，再把学到的东西写进我们自己的 UI skill `app-ui-design`，省得每次都靠吐槽。以后不管哪个模型写界面，都先读它。

它的核心是一个固定顺序：结构 → 层级 → 间距 → 字 → 色 → 细节 → 动效，后面的步骤救不了前面的错。AI 做的界面之所以丑，几乎都是跳过了前面的步骤，直接上色、全靠字号拉层级、所有按钮都做成实心。所以 skill 里有一条很具体的规则：一屏最多一个实心主按钮，次要操作用线框或浅底，辅助操作用纯文字。

素材来自 Refactoring UI 的 20 条原则、Emil Kowalski 的设计工程 skills（MIT 许可）、Apple 讲流体界面的分享、Material 3 和 iOS 设计规范，都用自己的话重写过。另外还有一份竞品拆解笔记。比如另一个 App 的「用量小票」，我们把 25 秒的录屏按每秒 2 帧抽成 50 帧，逐帧量出它的字号只有 4 档，纸从屏幕顶部往下「吐」，打印声是 7 段棘轮声。今日小票的打印动画就是照这个思路做的。

skill 的结构也照顾了额度。`SKILL.md` 只放总则和速查表，动效配方、Compose 写法、拆解笔记都放在 `references/` 里，用到哪份才读哪份，这种写法叫 progressive disclosure（渐进披露）。模型每次写界面，只为用得上的那几页付 token。

设计和代码靠 Figma 对齐。我在 Figma 里建了一套设计系统，变量和组件的 Android code syntax 直接写成代码里的 `XpColors`、`XpSpace`、`XpRadius`，和 `Tokens.kt` 一一对应。改设计先改 Figma 变量，再同步代码；以代码为最终依据，界面里不许写死颜色和间距。

skill 还要求用最坏情况的数据压测界面，比如超长的名字、空列表、很多条记录、加载失败；重要的部件先出几个方案并排比较。我在真机上吐槽一次，就往 skill 里写一条，之后所有模型都照着来。

### 一个功能怎么走完

<figure class="illu method">
  <img src="/citygenius-blog/assets/project-xiaopiao-loop.webp" alt="今日小票一个功能从想法到合并的流程图" width="1800" height="1510" loading="lazy" />
  <figcaption>一个功能从想法到合并的流程。需求和吐槽先进原话记录，定下来的写进 SPEC；Opus 把能拆的部分写成规格切片，经 Orca 派给 omp worker，界面主线自己写，颜色和间距取自 Figma 同名变量。做完先过测试和审查，再上真机按两种屏宽和 1.3 倍字体验收，最后由我合并。验收里发现的问题写回 skill。</figcaption>
</figure>

把上面这些串起来，一个功能在仓库里大致这样走完。我在真机上提需求或吐槽，先记进原话记录，定下来的写进 SPEC。Opus 读完 SPEC，把能拆出去的部分写成一份规格切片（spec slice），通过 Orca 派给 omp worker，在单独的分支上实现；界面主线由 Opus 自己写，动手前先读 UI skill，颜色和间距用 Figma 里的同名变量。写完先过测试和审查：Gradle 排队拿锁跑单元测试，再交给 Codex 或 audit 子代理挑错。然后是真机验收，360dp 和 411dp 两种屏宽、1.3 倍字体都要截图，主要页面挨个走一遍，只过编译和单测不算完成。最后由我合并。验收中发现的问题写回 skill。

写这篇的时候，我对照着读了 Anthropic 工程博客里讲 harness 的几篇文章，发现不少做法对得上。讲多 agent 研究系统的那篇说，每个子代理都需要目标、输出格式、工具和来源的指引，以及清楚的任务边界，否则 agent 会重复劳动、留下空白。讲上下文工程的那篇说，子代理可能花几万 token 去探索，交回来的只是一段 1000 到 2000 token 的浓缩总结。讲长时间运行应用的那篇写到，agent 给自己的活打分时「总是偏向正面」，所以审查和验收应该交给另一个角色。我把交叉审查交给另一家的模型、把真机验收单独列成一步，和这个结论方向一致。同一篇里还有一句我很认同：harness 里的每个组件，都是对「模型自己做不到什么」的一个假设。模型变强以后要重新测一遍，用不上的就删掉。

### 其他用到的 skill 和工具

- **Orca**：派 omp worker、监督并行任务、收结果。
- **Figma**：设计系统的变量和组件，和 `Tokens.kt` 同名。
- **ego-browser**：所有网页任务都用它，打开 Web 版、截图、测交互。
- **android-remote-control**：一个 MCP，让 agent 直接操作我的真机。
- **animate**：做动效时按它的顺序决定要不要动、用什么曲线、怎么打断。
- **archify**：画架构图，文中几张图都是用它生成的。
- **hooks**：上下文交接这类必须每次生效的规则，写成 hook，不写成提示词。

### 产品里的几个关键决定

<figure class="illu method">
  <img src="/citygenius-blog/assets/project-xiaopiao-arch-en.webp" alt="今日小票系统架构图" width="1600" height="847" loading="lazy" />
  <figcaption>今日小票的系统架构。Android App 在手机上解析支付通知，安全组里的原始数据不出手机，只有结构化字段发到云端；Web 版走同一套 API。云端的 Agent runtime 按问题打开对应的知识书，调用大模型生成回答，回答里的每个数字都要过一道「必须有出处」的校验。</figcaption>
</figure>

记账靠 Android 的 `NotificationListenerService` 读支付通知，付款、免密扣费、先享后付、自动续费、收款、退款都能识别。红包和转账的通知里看不到金额，就先记一笔「待填金额」。金额一律按整数「分」存，避免小数误差。

语音踩过一个坑。系统自带的 `SpeechRecognizer` 在我的 vivo 手机上从不回调，界面一直停在「在听」。后来换成端侧的 sherpa-onnx，中文小模型只有 25 MB，边说边出字，再配一份记账热词表；「三十五块五」会先转成 35.5 再进账本，录音和模型都留在手机上。

问账本的时候，AI 不能自己算。服务端的 Agent 通过只读工具取数，比如查账、按分类筛选、和上周同期对比，再用结果组织回答，过程用 SSE 流式推到界面上。回答发出去之前还有一道 grounding（溯源）校验，没有出处的数字不能出现。模型一开始只用 commandcode 的免费模型，现在线上主力换成了 DeepSeek v4.1 Flash，免费模型做后备，密钥只放在服务端。

## 结果

三周里，开发仓库的 main 分支上有 497 个提交。Android 端有 381 个 Kotlin 源文件，单元测试分布在 103 个文件里，共 911 处 `@Test`。提交署名里，Opus 5.5 有 180 次，Sonnet 有 84 次（集中在开头分道的两天），omp 里的 DeepSeek 有 70 多次。这些都是靠两份最低档订阅加一个不限量模型做出来的。

v0.5.0 的 APK 已经发在 GitHub 上，Android 8.0 以上能装。现在能用的功能有每日小票（打印、盖章、撕纸动效）、订阅侦探、用自然语言问账本、后悔模拟器、和家人朋友的小圈子，以及人格测试、决策转盘这类小游戏。

## 现状

整套配置放在 GitHub 的 [37chengshan/agent-harness](https://github.com/37chengshan/agent-harness)，包括共用的 `AGENTS.md`、四个 Haiku 子代理、`app-ui-design` skill、Orca 派活流程、SPEC 和原话记录模板，以及文中两张图的源文件。按 Anthropic 文章的建议，仓库里另外放了两个模板：一份功能清单 `features.json`，worker 只能改「通过 / 未通过」；一个 Stop hook，测试不通过就不许收工。

## 常见问题
### 为什么不让一个最强的模型全包？
没必要。不同的活需要的能力不一样：规划和写界面需要强模型盯着全局；按规格写后端、整理知识库这类边界清楚的活，交给擅长写量大代码的模型并行做；搜索调研用小模型就够了。写和审也该分开，换一家的模型做交叉审查，更容易发现原模型的盲区。额度紧只是让这种分工更划算。
### 最低档订阅真的够用吗？
够用的前提是主会话不干杂活。Opus 的额度只花在规划、前端和合并上，读文件交给 Haiku，大量代码交给 DeepSeek。最费额度的是返工，所以要先拷问需求、先写 SPEC。
### 几个 agent 同时写代码，不会互相改坏吗？
关键是先分道。每个 agent 只改自己道里的文件，共享文件谁都不碰，各自在 worktree 分支上提交，审过再合并。并行数量也要设上限，我现在最多开 5 个。
### 今日小票会把我的支付记录传到云端吗？
支付通知原文、账单原文和图片都在手机上解析，云端同步只用结构化字段。分享到圈子的小票只带分类合计，不带商户名和逐笔明细。不登录也能记账。
### 要买一台小票打印机吗？
不用。小票是屏幕上的动画，打印、盖章、撕纸都在 App 里完成。
