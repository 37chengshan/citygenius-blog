<b>一句话总结</b>
今日小票是我做的 Android 记账 App。它读支付宝和微信的支付通知自动记账，晚上把一天的花销打印成一张小票。这篇一半讲产品，一半讲它是怎么做出来的。我把整套开发方式叫作 37chengshan-harness：Opus 5.5 规划、写前端、派活，DeepSeek v4.1 Flash 写后端、干杂活、建知识库，Haiku 搜索、守住上下文，Codex 里的 GPT-6.1-sol 交叉审查和生图，卡住了再问 Fable 5.2。Claude 和 GPT 都只订了最低档，额度是要权衡的约束，分工还是按长处来。三周下来，开发仓库有 497 个提交、911 处单元测试，整套配置已经开源。
</div>

上大学以后，我一直有个需求，就是记账。可每次都坚持不了几天，每花一笔都要打开 App 选分类输金额，忙起来就忘了。我脑子里一直有个念头：要是有个 App 能自己把账记好，该多好。只是一直没时间，也没那股劲真去做。

上个月底，契机来了。我看到支付宝办的「智能体涌现奖（Emergent Agent Award）Season 1」，其中一个方向叫「生活好帮手」，比赛还有一个许愿池。我把许愿池里的数据整理清洗了一遍，去重后剩 812 条需求，最大的一类就是消费记账和财务，有 149 条；支持数最高的一条是「帮我揪出悄悄扣钱的自动续费」，298 个人点了支持。原来这么多人跟我想的一样。于是我开始从零搭这个 App。

它叫「今日小票」，一个 Android 原生 App，外加一个 Web 版和一个自己搭的 Node 服务。钱花出去就自动记一笔，晚上把这一天打印成一张小票，有明细、有合计，再配一句不说教的点评。三端都是我一个人做，Claude 和 GPT 各订了一份最低档。我把这一整套做法叫作 37chengshan-harness，就是套在模型外面的那层工程，管分工、上下文、工具和检查。配置整理成了开源仓库，文末有地址。

## 问题

产品这边，记账 App 已经够多了，难的是坚持，我自己就是例子。还有一点，AI 一碰到钱，最怕它顺手编个数字。

开发这边，开工两天就撞上了三件事。AI 写的功能是对的，界面却丑，我在真机上看完的原话是「按钮什么的做的好难看」。换个会话，定好的东西又被改回去，删掉的示例小票又冒了出来。同时开太多 agent，它们互相改来改去，什么都做不完。

额度也一直压着。最低档订阅按时间窗口算，Opus 这样的强模型跑一会儿就能把一个窗口用完，用完只能干等。三端的代码量摆在那里，强模型的每个 token 都得花在刀刃上。

## 做法

### 先把想法拷问清楚

写代码之前，我先用 grilling 这个 skill 让 AI 反过来追问我：主角是谁，做 App 还是 Web，怎么入账，数据能不能出手机。两轮问下来定了 11 条决策（D1 到 D11），写进 `docs/SPEC.md`。我没明确回答、按推荐默认的，就标成「假设」，随时能推翻。

SPEC 是整个项目的 single source of truth（唯一可信来源）。之后每改一次需求，都要在里面写清楚为什么改。新开的会话读完它，就知道现在要做什么、为什么这么做。这一步也最省额度。需求在对话里问清楚，花的是几轮问答；没问清楚就开工，返工烧掉的是成段的代码。

### 给每个模型分好活

  <img src="/citygenius-blog/assets/project-xiaopiao-harness.webp" alt="37chengshan-harness 的架构图" width="1800" height="1439" loading="lazy" />
  <figcaption>37chengshan-harness 的结构。左边是我和 Opus 5.5 主会话；主会话只做规划、前端和派发：搜索交给 Haiku 子代理，后端和杂活经 Orca 派给 omp 里的 DeepSeek，omp 的活提交在单独的分支上，审查后才合进 main。Codex 做第二意见和生图，Fable 5.2 只在卡住时出场。左下是所有模型共用的上下文：AGENTS.md、SPEC、skills，以及和 Tokens.kt 同名的 Figma 变量。</figcaption>
</figure>

分工就看两件事：这个模型最擅长什么，这件活要不要和别的活隔开。规划和写界面得有人盯全局，写代码的和审代码的要分开，读得多、结论少的搜索不能挤进主会话。

- **Opus 5.5** 负责规划、写前端和派活。它拆任务、写规格、写 App 的界面主线，能拆出去的活全派出去。开发仓库的提交署名里它出现了 180 次，从头到尾都在。
- **DeepSeek v4.1 Flash**（在 omp 里跑）写后端、干杂活、建知识库。这类活边界清楚、量大，照着写好的规格就能做好。Opus 先把规格写细，它照着实现，最后 Opus 再打磨一遍。提交署名 70 多次。
- **Haiku** 负责搜索和调研，真正的作用是守住主会话的 context window（上下文窗口）。翻仓库、查调用链、找开源实现，这类活读的文件多、留下的结论少，让 Opus 自己读，等于拿最贵的 token 读日志。Haiku 读完只交回一段 JSON，写着结论、文件位置和还缺什么。
- **Codex 里的 GPT-6.1-sol** 负责交叉审查和生图。换一家的模型来挑错，更容易看出 Claude 自己的盲区；落地页的照片也是它生成的。
- **Fable 5.2** 是顾问，只在三个时刻出场：定架构之前，同一个错第二次出现时，宣布高风险任务完成之前。

额度是在这套分工之上做的权衡。最低档的窗口很紧，所以 Opus 的额度只花在规划、前端和合并上；量大的活优先给 DeepSeek，它不限量，可以放开用；读文件的活交给 Haiku，主会话不碰。

子代理的边界写死在配置的 frontmatter 里，比口头约定靠谱。`search` 和 `grep` 只有只读工具；`audit` 多一个 Bash，但跑在 plan 模式下，只在隔离的 worktree 里审已经提交的代码。它们都声明了 `disallowedTools: advisor`，免得便宜的模型在后台偷偷调用贵的顾问；`omitClaudeMd: true` 让它们不加载主会话那份长长的规则，每次调用又省下一截。

DeepSeek 的活通过 Orca 派发。Orca 是一个多 agent 的 orchestration（编排）工具：主会话用 `run-create` 开一轮任务，用 `worker-start` 给每个 worker 一份自带上下文的说明，再用 `check --wait` 等结果回来，中间不用盯着。有一轮我并行派了三个 omp worker：两个做设置页和统计页的英文本地化，分别改了 2 个和 4 个文件，审完都合了进去；第三个做设置根页的转场，卡了 21 分钟，我叫停了，只留下 1 个有用的文件。worker 交付后先保留会话，下一个任务接着用，省得重新读一遍仓库。

这套分工也是一点点改出来的。第一天我用「分道」的办法，让几个 Sonnet agent 并行搭出了第一版：capture 管数据和通知识别，receipt 管主题和小票页，insights 管统计和徽章，merchant 管小店版和小游戏。每个 agent 只能改自己道里的文件，在自己的 worktree 分支上提交，不 push、不 merge。机器只有 16 GB 内存，四个 agent 共用，Gradle 构建要排队拿锁，规则里写死不许开模拟器。

第二天我让主会话只统筹、不写代码，实现全派给 worker。当晚就出了问题，我的原话是「代理直接改来改去根本完成不了任务」。于是全部叫停，App 主线改回 Opus 自己写，并行的 worker 以后最多 5 个。

现在回头看，并行适合边界清楚的活，比如按规格实现后端、分道搭骨架、跑测试。App 主线牵一发而动全身，交给一个模型从头写到尾更稳，也更省额度，最烧额度的就是来回返工。

### 把原话记下来

分工解决了「互相改坏」，没解决「忘了我要什么」。开工第二天做真机验收，我发现自己一直在重复同样的话，比如「为什么又有示例小票了，你现在就是 mock 数据啊」「不是我说的很清楚了啊」。

后来我在开发仓库里加了一份「原话记录」，把我提的产品和设计要求按时间逐字记下来，错别字和口语都不改，每条编号，再写清落到了哪里。规则只有一条，有冲突时以时间更晚的原话为准。设计文档引用时只写编号，不转述，免得一层层传话传歪。上面分工的每一次调整，也都记在这份文件里。

Anthropic 把这类事叫作 context engineering（上下文工程）。模型的注意力有限，放进上下文的每一行都该有用。我的办法是把要记住的东西都写进文件，用到时再读。三家工具共用同一份 `AGENTS.md`，Claude、Codex、omp 读到的规则一字不差；skill 只放在一个目录里，用软链接挂到每个工具下面。会话太长时，有一个 hook 会在自动压缩过一次、上下文又涨到 38 万 token 左右时拦下来，让当前会话写一份交接文档，新会话读完接着干，不靠模型硬记。

让 AI 写代码不难，难的是让它记住我说过的话。

### 专门做一个 UI skill

针对「界面丑」，我让 AI 去拆别人的 App，再把学到的东西写进我们自己的 UI skill `app-ui-design`，省得每次都靠吐槽。以后不管哪个模型写界面，都先读它。

它的核心是一个固定顺序：结构 → 层级 → 间距 → 字 → 色 → 细节 → 动效，后面的步骤救不了前面的错。AI 做的界面之所以丑，几乎都是跳过了前面几步，直接上色、全靠字号拉层级、所有按钮都做成实心。所以 skill 里有一条很具体的规则：一屏最多一个实心主按钮，次要操作用线框或浅底，辅助操作用纯文字。

素材来自 Refactoring UI 的 20 条原则、Emil Kowalski 的设计工程 skills（MIT 许可）、Apple 讲流体界面的分享、Material 3 和 iOS 设计规范，都用自己的话重写过。还有一份竞品拆解笔记。比如另一个 App 的「用量小票」，我们把 25 秒的录屏按每秒 2 帧抽成 50 帧，逐帧量出它的字号只有 4 档，纸从屏幕顶部往下「吐」，打印声是 7 段棘轮声。今日小票的打印动画就是照这个思路做的。

skill 的结构也照顾了额度。`SKILL.md` 只放总则和速查表，动效配方、Compose 写法、拆解笔记都放在 `references/` 里，用到哪份才读哪份，这种写法叫 progressive disclosure（渐进披露）。模型每次写界面，只为用得上的那几页付 token。

设计和代码靠 Figma 对齐。我在 Figma 里建了一套设计系统，变量和组件的 Android code syntax 直接写成代码里的 `XpColors`、`XpSpace`、`XpRadius`，和 `Tokens.kt` 一一对应。改设计先改 Figma 变量，再同步代码；最终以代码为准，界面里不许写死颜色和间距。

skill 还要求拿最坏情况的数据压测界面，比如超长的名字、空列表、成堆的记录、加载失败；重要的部件先出几个方案并排比。我在真机上吐槽一次，就往 skill 里写一条，之后所有模型都照着来。

### 一个功能怎么走完

<figure class="illu method">
  <img src="/citygenius-blog/assets/project-xiaopiao-loop.webp" alt="今日小票一个功能从想法到合并的流程图" width="1800" height="1510" loading="lazy" />
  <figcaption>一个功能从想法到合并的流程。需求和吐槽先进原话记录，定下来的写进 SPEC；Opus 把能拆的部分写成规格切片，经 Orca 派给 omp worker，界面主线自己写，颜色和间距取自 Figma 同名变量。做完先过测试和审查，再上真机按两种屏宽和 1.3 倍字体验收，最后由我合并。验收里发现的问题写回 skill。</figcaption>
</figure>

串起来看，一个功能在仓库里大概这样走完。我在真机上提需求或吐槽，先记进原话记录，定下来的写进 SPEC。Opus 读完 SPEC，把能拆出去的部分写成一份规格切片（spec slice），通过 Orca 派给 omp worker，在单独的分支上实现；界面主线由 Opus 自己写，动手前先读 UI skill，颜色和间距用 Figma 里的同名变量。写完先过测试和审查，Gradle 排队拿锁跑单元测试，再交给 Codex 或 audit 子代理挑错。然后是真机验收，360dp 和 411dp 两种屏宽、1.3 倍字体都要截图，主要页面挨个走一遍，只过编译和单测不算完成。最后由我合并，验收中发现的问题写回 skill。

写这篇的时候，我对照着读了 Anthropic 工程博客里讲 harness 的几篇文章，不少做法对得上。讲上下文工程的那篇说，子代理可能花几万 token 去探索，交回来的只是一段 1000 到 2000 token 的浓缩总结。讲长时间运行应用的那篇写到，agent 给自己的活打分时「总是偏向正面」，所以审查和验收该交给另一个角色，我把交叉审查交给另一家的模型、把真机验收单独列成一步，也是这个意思。同一篇里还有一句我很认同：harness 里的每个组件，都是对「模型自己做不到什么」的一个假设，模型变强以后要重新测，用不上的就删掉。

### 通知怎么读到

<figure class="illu method">
  <img src="/citygenius-blog/assets/project-xiaopiao-arch-en.webp" alt="今日小票系统架构图" width="1600" height="847" loading="lazy" />
  <figcaption>今日小票的系统架构。Android App 在手机上解析支付通知，安全组里的原始数据不出手机，只有结构化字段发到云端；Web 版走同一套 API。云端的 Agent runtime 按问题打开对应的知识书，调用大模型生成回答，回答里的每个数字都要过一道「必须有出处」的校验。</figcaption>
</figure>

自动记账靠 Android 的 `NotificationListenerService`。在系统设置里授权以后，`PaymentListenerService` 只听支付宝和微信这两个包的通知，别的 App 一概不看。通知一到，它先记一笔「这条通道还活着」，再跳过分组摘要，取出标题和最长的那段正文，交给手机上的解析器。付款、免密扣费、先享后付、自动续费、收款、退款都能认出来。红包和转账的通知里看不到金额，就先记一笔「待填金额」；花呗的账单提醒会变成一条「待还账单」，不算进支出。金额一律按整数「分」存，避免小数误差。

国产系统在这里有个坑。重装、被省电策略冻结之后，监听服务经常悄悄断开，App 自己根本不知道。所以服务一断开就会安排一次自动修复，接入页面上也能看到最近一次收到通知是什么时候、来自哪个 App。另外，支付 App 常常把同一笔钱推两次，先来一条光秃秃的「支出」，再来一条带商户名的「付款成功」，所以前后 2 分钟内同方向、同金额的通知只记一笔。

### 数据存在哪

账本、通知记录和每晚的来信都存在手机上的 Room 数据库里（底下是 SQLite），开关和偏好放在 DataStore。每条读到的支付通知都会原样存一份到 `capture_log` 表，连同处理结果：已记账、重复已跳过、已忽略、待填金额，或者没认出。这张表只留最近 200 条，多出来的自动删掉，也从不上传。在 App 里打开「数据与隐私 → 通知记录」，每条通知被怎么处理的都看得到。

App 关掉了系统备份（`allowBackup="false"`），本地库不会跟着系统备份到别处。登录以后的同步也只推结构化的账目字段，改过的行打上标记等着推送，删掉的行留一块 tombstone（墓碑），好让云端也跟着删。服务端写好的「夜间来信」拉下来后在本地存一份，没网也能翻。

### 怎么测，反馈怎么回来

解析器最容易出错，所以测得最多。`PaymentNotificationParserTest` 里攒了一份通知语料，每条写清楚该记成多少钱、算什么类型，或者该忽略；去重、商户分类、金额规则也各有一组单测。全仓库一共 911 处 `@Test`，跑的时候 Gradle 排队拿锁。

光有单测还不够，还得看真的通知能不能走通整条链路。所以我写了一个很小的测试 App 叫 notifake，只装在模拟器上。它冒充支付宝和微信的包名发假通知，里面的 11 条样例和解析器单测用的是同一批，测试里说能认出的，屏幕上就真能看到。它还能用 adb 一行命令触发，agent 不用等我点手机，自己就能跑一遍。这些都过了，才轮到真机验收。

真实世界的通知总比语料多。通知记录里「没认出」的那条，可以直接点「反馈给开发者」：要发出去的内容原样摆在面前，可以先改，点了发送才会发。它会进服务端的 `feedback` 表，类型是 `capture_miss`。我用一个只读脚本把这些反馈拉出来，原文一字不改地抄进解析器单测当回归用例，再去修规则，处理状态记在一份台账里。目前回来的几条里，支付宝一笔「11.90元的免密/自动扣款」一开始没认出，补了规则；微信的「昨日记账日报」和支付宝的「红包即将失效」其实是营销，现在直接忽略；花呗的账单提醒以前也没认出，现在记成待还账单。

### 隐私怎么守

支付通知很私密，所以数据规则写在 `AGENTS.md` 最前面，三家模型都得照着来。

- 通知原文、账单原文和图片只在手机上解析，云端只拿结构化字段。
- 通知原文不会自己离开手机，唯一的出口是上面那个反馈，发什么你看得见，也改得了。
- 日志里只写规则编号和金额，不写通知正文。
- 吃饭、运动、体重这类生活数据默认只存本机，同步到账号要自己单独打开，随时能关。
- 数据贡献默认关闭，要单独授权，也能撤回；商家那边只看聚合数据，样本少于 20 的格子不展示。
- 分享到圈子的小票只带分类合计，不带商户名和逐笔明细。
- 大模型的密钥只放在服务端；服务端的安全日志不记 IP 和账号，请求按 IP 限流，密码用 scrypt 存。

不登录也能记账。

### 语音和问账本

语音踩过一个坑。系统自带的 `SpeechRecognizer` 在我的 vivo 手机上从不回调，界面一直停在「在听」。后来换成端侧的 sherpa-onnx，中文小模型只有 25 MB，边说边出字，再配一份记账热词表；「三十五块五」会先转成 35.5 再进账本，录音和模型都留在手机上。

问账本的时候，AI 不能自己算。服务端的 Agent 通过只读工具取数，比如查账、按分类筛选、和上周同期对比，再拿结果组织回答，过程用 SSE 流式推到界面上。回答发出去之前还有一道 grounding（溯源）校验，没有出处的数字不能出现。一开始只用 commandcode 的免费模型，现在线上主力换成了 DeepSeek v4.1 Flash，免费模型做后备。

### 其他用到的 skill 和工具

- **Orca**：派 omp worker、监督并行任务、收结果。
- **Figma**：设计系统的变量和组件，和 `Tokens.kt` 同名。
- **ego-browser**：所有网页任务都用它，打开 Web 版、截图、测交互。
- **android-remote-control**：一个 MCP，让 agent 直接操作我的真机。
- **animate**：做动效时按它的顺序决定要不要动、用什么曲线、怎么打断。
- **archify**：画架构图，文中几张图都是用它生成的。
- **hooks**：上下文交接这类必须每次生效的规则，写成 hook，不写成提示词。

## 常见问题
### 为什么不让一个最强的模型全包？
没必要。不同的活要的能力不一样：规划和写界面需要强模型盯着全局；按规格写后端、整理知识库这类边界清楚的活，交给擅长写大量代码的模型并行做；搜索调研用小模型就够了。写和审也该分开，换一家的模型做交叉审查，更容易发现原模型的盲区。额度紧只是让这种分工更划算。
### 最低档订阅真的够用吗？
够用的前提是主会话不干杂活。Opus 的额度只花在规划、前端和合并上，读文件交给 Haiku，大量代码交给 DeepSeek。最费额度的是返工，所以要先拷问需求、先写 SPEC。
### 几个 agent 同时写代码，不会互相改坏吗？
关键是先分道。每个 agent 只改自己道里的文件，共享文件谁都不碰，各自在 worktree 分支上提交，审过再合并。并行数量也要设上限，我现在最多开 5 个。
### 今日小票会把我的支付记录传到云端吗？
不会传原文。支付通知原文、账单原文和图片都在手机上解析，原始通知只在手机里留最近 200 条，云端同步只用结构化字段。分享到圈子的小票只带分类合计，不带商户名和逐笔明细。不登录也能记账。
### 要买一台小票打印机吗？
不用。小票是屏幕上的动画，打印、盖章、撕纸都在 App 里完成。
